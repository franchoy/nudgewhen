## Maintainer-authorized architecture freeze (this task)

The maintainer authorized the following Phase 1 architecture freeze for
this Build. The freeze is recorded in this experiment as
maintainer-supplied evidence.

- Domain model: `Reminder { id: String, text: String }`. No other fields.
  No time semantics.
- Textual creation contract: trim leading/trailing whitespace; reject when
  empty; persist the normalized trimmed text; no parsing or
  interpretation.
- Display and ordering: every stored reminder displayed; persisted list
  order is creation/display order; oldest first; new reminder appends to
  the end; removal preserves relative order.
- Lifecycle-ending semantic: PERMANENT REMOVAL. No completion state.
- Ownership boundary:
  - `io.github.franchoy.nudgewhen.domain` owns `Reminder`,
    `ReminderStore`, `ReminderController`.
  - `io.github.franchoy.nudgewhen.data` owns `FileReminderStore`.
  - `io.github.franchoy.nudgewhen.ui` owns `ReminderScreen`.
  - `MainActivity` and `ui.theme` remain the existing Android entry point
    and theme boundary.
  - Domain, controller, and store implementations remain
    Android-framework independent.
- Persistence technology: single app-private file; standard Java/Kotlin
  runtime file APIs only; no production persistence dependency. Room,
  raw SQLite, DataStore, SharedPreferences, Gson, Moshi,
  `kotlinx.serialization`, and `org.json` are excluded for production
  persistence.
- Persistence format: file name `reminders-v1.txt`; UTF-8; first line
  `NWR1`; subsequent lines `<id><TAB><base64url-encoded UTF-8 reminder
  text>`; record order equals creation/display order; unsupported or
  malformed format must not be silently reinterpreted.
- Store contract: `load(): List<Reminder>` and
  `save(reminders: List<Reminder>)`. Mutation ordering: derive, persist,
  then expose only after persistence succeeds.
- Identity: opaque strings; production implementations may use
  `java.util.UUID.randomUUID().toString()`; ordering does not derive from
  the identifier; tests must be able to supply deterministic identifiers;
  no time-derived IDs.
- UI and state ownership: plain Kotlin `ReminderController` plus
  Compose-owned presentation state; no Android `ViewModel`; no navigation
  framework; `MainActivity` remains the single Android composition entry
  point.
- Restore-after-restart: synchronous during normal `MainActivity`
  startup, before presenting the reminder list; no `Flow`, background
  restoration, `WorkManager`, `AlarmManager`, `Service`,
  `BroadcastReceiver`, `androidx.startup` initializer, network, sync, or
  loading/retry architecture.
- Test boundary: ordinary local JVM tests under
  `app/src/test/kotlin/...`; Phase 2 owns deterministic tests for
  `Reminder`, `ReminderController`, lifecycle behavior, and input
  normalization; Phase 3 owns deterministic tests for `FileReminderStore`,
  format round-trip, ordering, removal persistence, and restore from a
  new `FileReminderStore` instance, using temporary files; no instrumented
  Android test is required for domain/persistence proof; the exact
  Kotlin/JVM test-library dependency is NOT selected in Phase 1 and must
  be selected and authorized in Phase 2.
- Validator/CI future boundary: separately authorized validator evolution
  must make the deterministic JVM tests part of release evidence before
  Phase 2 can close; preferred minimum future change is to extend the
  EXISTING android validation surface to execute `:app:testDebugUnitTest`;
  that validator change is NOT part of Phase 1B.
- Frozen release non-goals: voice, speech, notifications, time
  scheduling, alarms, location, geofencing, contextual/device-state
  triggers, background execution, networking, sync, analytics,
  additional Android activities, services, receivers, providers, new
  Android permissions, production-readiness guarantees, Hermes, MCP,
  provider migration/reversion.
