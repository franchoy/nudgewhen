## Product-scope design

The current still-v0.1.1 release contract now carries a release-neutral product-scope extension:

```
"product_scope": {
  "allowed_capabilities": []
}
```

Closed machine-readable capability vocabulary:

- `reminders`
- `notifications`
- `voice-or-speech`
- `location-or-geofencing`
- `persistence`
- `networking`
- `background-behavior`

Contract validation establishes:

- `product_scope` must be a JSON object.
- `allowed_capabilities` must be a list.
- Each entry must be a non-empty string.
- Unknown identifiers fail.
- Duplicate identifiers fail.

Charter consistency establishes:

- No release-version literal controls authorization.
- Unauthorized positive / non-negated capability claims fail.
- Authorized positive claims are permitted.
- Authorization does not require positive prose.
- Negated or explicit non-goal occurrences remain permitted.
- An explicit `Non-goals` / `Explicit non-goals` / `Out of scope` section remains mandatory.
- Inline negation retains the historical approximately ±300-character window while clamping that window to the containing Markdown `##` section.

Current active v0.1.1 therefore still positively authorizes no machine capability because `allowed_capabilities` is the empty list. v0.1.2 is NOT active in the contract yet.
