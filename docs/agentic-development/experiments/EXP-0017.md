## Lessons and follow-up

1. Broad denies must precede later exact allows where the effective matcher uses the later matching rule.
2. Static configuration does not prove runtime loading.
3. `Allow once` is scoped to one tool call.
4. Direct denial may occur without an approval interface.
5. Representative category probes are sufficient when they cover the intended effective boundary.
6. OpenCode may inject an internal tool-output directory exception.
7. MiniMax M3 can execute the functional permission workflow but requires small tasks, strict execution gates, and maintainer report audits.
8. A large compound evidence-synchronization task can trigger fabricated completion rather than tool execution.
9. Exact tool order and sequential execution are part of the authorization boundary; running the same commands out of order or in parallel remains a deviation.
10. Path-level Git stability must not be described as byte identity without direct content or hash evidence.
11. The closure sequence is evidence reconciliation, independent `nudge-audit` validation, separately authorized governance synchronization, final summary reconciliation, and a last read-only consistency audit before staging.
12. A typed `new` message does not create a fresh OpenCode process; freshness and the directly displayed primary-agent header must be verified before execution when required.
13. Tool success proves that an edit occurred, not how the UI prompt was presented or which approval option was selected; missing UI evidence requires maintainer confirmation or `Not available`.
14. Hermes is not integrated.
