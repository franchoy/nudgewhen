## 5. Independent technical corrections preserved in this record

Three corrections were supplied by the maintainer as independent technical
corrections to the Phase 1A recommendations. All three are preserved here and
all three are carried into the architecture candidate.

### 5.1 Strict ISO parser behavior

The Phase 1A recommendation asserted that Java's predefined
`DateTimeFormatter.ISO_LOCAL_DATE_TIME` uses `SMART` resolver style by
default. That assertion was incorrect and is withdrawn. The predefined ISO
formatters resolve with `ResolverStyle.STRICT` and the ISO proleptic
chronology.

The candidate specifies an explicitly constructed formatter with
`ResolverStyle.STRICT` pinned on the instance, so that the pattern, the
resolver style, and the proleptic-year field are explicit properties of the
persisted contract rather than inherited defaults.

**Evidence class:** maintainer-supplied technical correction, accepted as the
authoritative drafting instruction. It was not independently re-verified by
execution in this Build; no such command was authorized.

### 5.2 Nullable epoch representation

The Phase 1A recommendation objected to a nullable epoch-millisecond
representation on the grounds that it would collide with epoch zero. That
objection was incorrect and is withdrawn. A nullable `Long?` does not collide
with epoch zero: `null` is the absent marker and `0L` is a legitimate
epoch-millisecond value.

The candidate records the actual objection, which is semantic rather than
representational: an epoch-millisecond value is a UTC timeline coordinate, and
presenting it as the local date and time the user chose requires a timezone
conversion that the release charter explicitly excludes.

**Evidence class:** maintainer-supplied technical correction, accepted as the
authoritative drafting instruction.

### 5.3 Non-atomic filesystem writes

The Phase 1A recommendation described the persistence write as an atomic
filesystem replacement with guaranteed preservation of prior on-disk bytes
after an I/O failure. That description was incorrect and is withdrawn. The
observed implementation writes with `file.writeBytes(encoded)`, which
truncates and rewrites the target file in place and is not a crash-safe
atomic replacement.

The candidate claims only the guarantee that does hold: validation of the
complete input list before the target file is opened or truncated.

**Evidence class:** maintainer-supplied technical correction, accepted as the
authoritative drafting instruction. The underlying write behavior was
directly observed in this Build by reading
`app/src/main/kotlin/io/github/franchoy/nudgewhen/data/FileReminderStore.kt`.
