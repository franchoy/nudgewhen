### 8.1 Plan finding (historical)

```text
ID lookup → validation → unchanged comparison → effective change
```

This observation is preserved as the Plan's original finding. It is not
withdrawn, and it is not merged with the later independent correction below.

### 8.2 Independent review correction

Independent review (maintainer-supplied).

The accepted architecture already specifies this ordering. The planning task's
authorized architecture read ended at line 383, before §3.4. Consequently, the
Plan's apparent ambiguity was caused by **limited authorized inspection**, not by
a missing architectural decision.

Option A — `ID lookup → validation → unchanged comparison → effective change` —
was therefore **already frozen by the accepted Phase 1 contract**. The later
Phase 2B Build authorization reaffirmed the already-frozen ordering; it did not
create a new architecture decision, and this record does not create one. The
ordering was already fixed in the accepted and frozen Phase-1 contract.

Direct (Phase 2C evidence-reconciliation stage), from
`docs/releases/v0.1.5/reminder-time-architecture.md`, re-confirmed by direct
observation in the present corrective task:

- line 383 is the final line of §3.3 ("Additional invariants"), and line 384 is
  the §3.4 heading — so a read terminating at line 383 stops immediately before
  the normative comparison section;
- §3.2 records that **ID lookup occurs before time validation**, so a missing id
  is a `false` result even when the supplied time would be invalid;
- the §3.4 comparison table records the validation order of the accepted
  `setTime` as **after ID lookup, before the unchanged check**, and §3.4 closes
  by stating that placing validation after the lookup keeps the missing-id
  contract stable.

**Inferences.**

- Inference: the Plan's recommended ordering was derived from the frozen
  contract rather than from a new architectural choice, because the recommended
  sequence is identical to the §3.4 ordering. This is supported by, but not
  proven by, the review finding.

**Corroborating evidence.**

- Corroboration (maintainer-supplied): the Phase-2B Build authorization and the
  Phase-2B implementation both followed the already-frozen ordering, which
  corroborates that the ordering was fixed before Phase 2B began.

**Lessons supported by this experiment.**

- When a planning task's outcome depends on a normative section of an accepted
  contract, the authorized read range must cover that complete section. A range
  that stops immediately before the decisive subsection can produce a
  well-reasoned but unnecessary ambiguity finding.
- A read-range boundary is an authorization artifact, not a design input, and
  should be reported as such rather than treated as an unresolved product
  question.
- A post-task independent review is a review activity, not an in-session
  maintainer corrective prompt, and the two must not be counted as the same
  event type.

rests on a single observation in this record; under the experiment protocol a
single observation is recorded but does not change project rules.
